# 推薦履歴・成績比較・改善の運用

## 対象と前提

推薦時点の入力を固定し、その後の株価を継続記録する。最新画面では従来どおり現在の指標を見せ、履歴画面では当時の指標・理由を表示する。再生成しても過去の公開版を消さない。

現在の銘柄選定・順位・3段階評価はルールが決め、AIは理由を書く。公開推薦とルール上位10件が一致する日は両者の成績も同じになる。AIの理由不備で銘柄が除かれた場合に差が生じても、AIの選別能力の証拠とはしない。理由文の品質と選定ルールの投資成績を分けて改善する。

## 蓄積する情報と頻度

| 情報 | 頻度 | 内容 |
|---|---|---|
| 生成試行 | 自動・手動生成のたび、AI呼び出し前 | 株価基準日、元バッチID、時刻、モデル、プロンプト版、ルール版、アプリ版、実際の入力JSON |
| 候補 | 生成試行ごと | ルール上位最大50件、ルール順位、当時の全画面指標、テーマ名、財務書類ID・開示日時。実際のAI入力はこのうち上位最大10件 |
| 応答と公開結果 | 生成試行ごと | 応答JSON、成功・失敗、エラー、公開順位・評価・理由、公開時刻。同日の初回公開版だけを主比較対象にする |
| 終値・分割係数 | 日次バッチの計算後 | 候補銘柄と1306。変化した観測を追記し訂正前も残す |
| 財務・予想・配当方針 | 追跡実行時、内容変更時のみ | annual・quarterly・forecast・EDINETの観測時点の内容。取得時刻だけの変化では追記しない |
| 成績 | 日次 | 最新、21・63・126・252営業日。結果のJSONが変わった場合だけ追記 |
| 比較レポート | 日次追跡の完了時 | 版・期間ごとの対応付き比較、未到達・不足件数、月別の差 |
| 改善判断 | 月次を推奨、現時点は人手 | 欠損確認、失敗条件の調査、改善仮説と採否の記録 |

財務等の記録は取得元テーブルの最新状態を観測する方式で、観測の間に更新されたすべての中間版を保証しない。EDINETの同期は価格同期と並列なので、更新が次回追跡で記録されることがある。入力全文はDBに保持するが履歴APIには返さない。

## 成績計算

- 公開日の翌市場営業日の終値を開始価格に固定する。公開当日の終値では購入できたと仮定しない。開始日を後から価格のある日にずらさない。
- 開始日から21・63・126・252営業日後を期限とする。最新値は最大252営業日まで。比較の主期間は126営業日。
- 市場営業日は内閣府祝日と既存の取引日判定から作る。銘柄の価格観測日で期間を短縮しない。祝日データが対象年を覆わなければ実行を失敗させる。
- 開始翌日から評価日までの分割・併合を調整した株価収益率と、銘柄ごとの最大下落率を計算する。配当・税・取引費用は含まない。
- 期間未到達はpending、必要価格が欠ける場合はdata_missing。開始価格が20市場営業日たってもない場合はentry_unavailable。欠損をゼロ収益として扱わない。
- 公開推薦、ルール上位10件、保存候補全体は等金額の平均収益率で比較。全構成銘柄の同じ開始日・終了日の結果が揃った場合だけ集計する。集計ポートフォリオの最大下落は未計算で、個別下落率の平均を代用しない。
- 1306は市場比較用の株価成績。配当込みTOPIXとは区別する。
- 旧データは理由と順位を移すが、当時の指標や実際の公開時刻は推定しない。legacy_incompleteとして成績比較から除く。

## 比較と改善

モデル・プロンプト版・ルール版・評価期間ごとに、同日の初回公開版とルール上位10件を対応させる。満期かつ両側の期間が一致する組だけで平均成績、平均差、差の中央値、上回った割合、同率件数、ユニーク銘柄数、推薦月別の平均差を計算する。再生成の良い結果だけを選ばない。

異なる版の平均をそのまま優劣と解釈しない。同じ銘柄の連続推薦と保有期間の重なりがあるため、推薦日数は独立した試行数ではない。年率の実口座運用成績とも区別する。

改善手順は次のとおり。

1. 月次に不足・未到達・理由不備を先に調べる。業種、利回り、配当余力など、成績が悪化した条件を分析する（条件別集計は現時点では人手）。
2. 選定ルールについて仮説を1つ決める。変更前に評価期間、比較対象、採用基準を定める。プロンプト改善では根拠の正確さ・欠落・誤った断定の減少を主に評価する。
3. 将来の同じデータで現行版と改善版を並走させる。過去の結果を見てから作った指示を過去入力で再実行した結果だけで効果を主張しない。
4. 126営業日成績、下落、減配、集中度、期間差を人が確認して採用する。十分な期間・件数がなければ継続観測する。

改善版の保存・並走実験・自動採用、配当込み収益率、減配イベント集計、不確実性区間、全市場の入力保存は未実装。第1版は蓄積と株価比較までで、自動的に学習・設定変更しない。

## 運用と保持

`batch-cli evaluate-recommendations` を日次の `compute --label daily` の後に実行する。引け前（JST16時未満）の手動実行は前日までを対象にする。評価途中の行は画面に公開せず、バッチの完了状態とレポートを最後に確定する。失敗時は再実行でき、途中結果は比較から除く。

マイグレーション `0021_recommendation_tracking.sql` をWorker公開より先に適用する。最新表示用のrecommendationsを維持するため旧Workerへ切り戻せるが、旧Workerによる生成は新履歴を残さない。

履歴・価格訂正版・入力の自動削除は行わない。上位50候補、年間250営業日なら候補行は年間約12,500件（手動生成を除く）。最新成績は日次で増えるため、期限別の確定結果だけで容量を見積もらない。全過去runを日次再計算する第1版であり、蓄積量に応じて満期runの再計算範囲と保管先を改善する。未公開pendingの自動回収は未実装。

検証はRustの計算・比較・生成テストと、`python3 scripts/test_recommendation_tracking.py` による実SQLのSQLiteテスト。後者は再生成時の履歴保持、失敗時の旧公開版維持、部分保存の不可視性、訂正と再実行を確認する。

## 履歴画面の表示量

画面表記は「レコメンド」に統一する。公開履歴は新しい順に20回ごとに前後へ切り替え、追加取得で選択肢を無制限に増やさない。各回の銘柄一覧は10件単位で表示し、候補表示の切り替え時に先頭へ戻す。理由文と全体比較は折りたたみ、必要なときに開く。履歴・詳細の取得失敗はそれぞれ再読み込みでき、再生成後は最新ページから取得し直す。
